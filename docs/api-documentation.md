# API documentation

Kit's API reference and OpenAPI spec are generated by [Scribe](https://scribe.knuckles.wtf) from
attributes on the controllers. Three things keep them honest: contract tests that compare the spec
with the running API, a test that refuses unfinished documentation, and
[legible](https://github.com/JustSteveKing/legible), which checks the spec is usable by an agent.

## Generating it

```bash
php artisan scribe:generate --no-interaction
```

That writes:

| File | What it is |
| --- | --- |
| `public/docs/index.html` | The HTML reference, served at `/docs` |
| `public/docs/openapi.yaml` | The OpenAPI spec |
| `public/docs/collection.json` | A Postman collection |
| `.scribe/` | Scribe's intermediate files |

Commit `public/docs/` and `.scribe/` with the endpoint change that caused them. The test suite
also runs Scribe, so expect timestamp churn after a test run; leave that out of your commits.

The spec is advertised from the API catalog at `/.well-known/api-catalog`, so tools that find your
API can find its description too.

## Writing the documentation

Endpoints are documented with PHP attributes on the controller class. `make:endpoint` writes the
skeleton; `LoginController` is a finished example.

```php
#[Group(name: 'Authentication')]
#[Subgroup(name: 'Token Authentication')]
#[Endpoint(
    title: 'Login',
    description: 'Exchange an email and password for a bearer token. Use it when a user signs in on a new device, naming the device in device_name. Returns the user with the token, its type and expiry in meta; wrong credentials are a 422 on the email field.',
)]
#[Unauthenticated]
#[BodyParam('email', type: 'string', description: 'User email address.', required: true, example: 'jane@example.com')]
#[ResponseFromApiResource(
    name: UserResource::class,
    model: User::class,
    status: 200,
    description: 'Login succeeded.',
    additional: ['meta' => ['token' => '1|example-token', 'token_type' => 'Bearer', 'expires_at' => null]],
)]
// ...a #[Response] for each error status
final class LoginController
```

What each attribute is for:

- **`#[Endpoint]`**: the description has three sentences: what the endpoint does, when a client
  should call it, and what it returns. An agent choosing between tools reads exactly that.
- **`#[BodyParam]`, `#[QueryParam]`, `#[UrlParam]`**: one per input, with a realistic example.
- **`#[ResponseFromApiResource]`**: the success response, built from the real resource.
- **`#[Response]`**: one per error status the endpoint can return, written as a problem details
  document. Kit's generator documents these as `application/problem+json`.
- **`#[ResponseField]`**: a field's type when its example cannot show it, such as a nullable
  integer whose example is `null`.

## What Kit adds to Scribe

Scribe needs a little help with an API shaped like this one. `config/scribe.php` and
`AppServiceProvider` set it up:

- Routes are matched on `v1/*`, since there is no `/api` prefix.
- Path parameters keep the names the routes give them, rather than Scribe's guessed `{id}`.
- `ProblemDetailsOpenApiGenerator` documents every `4xx` and `5xx` response as
  `application/problem+json`.
- `NoContentOpenApiGenerator` documents a `204` as having no body.
- `ResponseFieldsOpenApiGenerator` applies each `#[ResponseField]`'s type and nullability, which
  Scribe would otherwise guess from the example.

Two Scribe limits worth knowing: it documents only the first HTTP method of a route, so a
`GET, POST` pair needs two routes, each with its own controller. And it cannot run twice in one
PHP process, which is why the tests generate the spec once and share it.

## Contract tests

`tests/Feature/OpenApiContractTest.php` checks the spec against the application in three ways:

1. **Coverage.** Every `v1/` route must be in the spec. A route Scribe cannot see fails the build.
2. **No TODOs.** Any `TODO` left by `make:endpoint` fails the build, so an endpoint cannot ship
   with placeholder documentation.
3. **Runtime checks.** A list of real requests is made against the application, and each response's
   status, media type and body are validated against what the spec says for that status.

The third is the one that catches drift: rename a resource field without updating the attributes,
and the test fails. Add each new endpoint to the runtime checks; `make:endpoint` reminds you.

## legible

legible scores an OpenAPI spec for agent readiness: the things that trip up an LLM calling the API
as tools, such as a vague description, two operations with the same description, an error status
with no documented response, or a parameter that appears in both the path and the body.

```bash
legible check public/docs/openapi.yaml
```

`.legible.yaml` fails the build on any warning, or a score under 95. When a finding is right for
your API, add it to `ignore` with a `reason`, rather than lowering the bar:

```yaml
ignore:
  - rule: error-shape
    operations:
      - POST /v1/projects
    reason: >
      Validation problems add an errors member keyed by field, which apiguide.dev's
      validation-failed type defines.
```

`legible explain <rule>` says why a rule matters. legible is a single binary from its
[releases](https://github.com/JustSteveKing/legible/releases); CI pins the version and checks its
checksum.
